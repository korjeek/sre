# Отчёт

### Какие абстракции Kubernetes использованы

| Абстракция | Имя | Зачем |
| --- | --- | --- |
| Namespace | `sre` | Изолирует все ресурсы приложения от дефолтного пространства имён. |
| ConfigMap | `api-config` | Хранит нечувствительные параметры: `PORT`, `LOG_LEVEL`, `STATIC_DIR`, `MIGRATIONS_DIR`. |
| Secret | `db-credentials` | Безопасно хранит логин/пароль PostgreSQL и `DATABASE_URL`. |
| StatefulSet | `postgres` | Запускает БД с устойчивой идентичностью и собственным томом. |
| PersistentVolumeClaim | `pgdata-postgres-0` | Создаётся автоматически через `volumeClaimTemplates`; данные БД переживают перезапуск пода. |
| Service (headless) | `postgres` | Создаёт стабильное внутреннее DNS-имя `postgres:5432` для адресации пода базы данных. |
| Job | `migrate` | Гарантирует одноразовое применение SQL-миграций до успешного завершения. |
| Deployment | `api` | Управляет stateless-приложением (2 реплики), легко масштабируется через `kubectl scale`. |
| Service (NodePort) | `api` | Предоставляет внешний доступ к UI на порту 30080 и балансирует трафик между подами `api`. |
| Probes | readiness/liveness | Проверяют здоровье контейнеров: эндпоинт `/healthz` у `api` и утилита `pg_isready` у `postgres`. |
| initContainers | `wait-for-postgres`, `wait-for-schema` | Упорядочивают и синхронизируют запуск зависимостей кластера. |

### Как сервисы взаимодействуют

1. **Внешний трафик:** Браузер обращается к Service `api` (NodePort 30080). Балансировщик выбирает один из готовых подов `api` (ориентируясь на успешную readiness-пробу `/healthz`) и отдаёт статику UI или обрабатывает REST JSON (`/api/services`, `/api/incidents`).
2. **Связь с СУБД:** Поды `api` подключаются к PostgreSQL по `DATABASE_URL` из Secret. Хост `postgres` разрешается через headless Service напрямую в адрес пода `postgres-0`. Состояния в подах `api` нет, поэтому реплик может быть сколько угодно (ограничение: `MaxConns=10` на под).
3. **Порядок старта:**
    - Стартует под `postgres-0` и переходит в статус Ready после успешной проверки `pg_isready`.
    - Job `migrate` запускает init-контейнер `wait-for-postgres`, дожидается готовности порта 5432, после чего основной контейнер создаёт схему и seed-данные.
    - Поды `api` ждут в своем initContainer (`wait-for-schema`) появления таблицы `incidents` и только после этого запускают основное приложение, начиная принимать клиентский трафик.
