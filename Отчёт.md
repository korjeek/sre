# Отчёт: Victoria Metrics и экспорт метрик

Метрики приложения SRE Incident Tracker (namespace `sre`) и PostgreSQL собираются в Victoria Metrics, развёрнутую в этом же кластере minikube (namespace `monitoring`). Манифесты лежат в `k8s/`, настройки Victoria Metrics — в `k8s/monitoring/`.

## 1. Стек

| Компонент | Что используется |
|---|---|
| Приложение | Go, `net/http`, PostgreSQL 16, minikube (namespace `sre`) |
| Хранилище метрик | Victoria Metrics Single, helm-чарт `vm/victoria-metrics-single`, релиз `vm-single`, namespace `monitoring` |
| Метрики приложения | клиентская библиотека `github.com/prometheus/client_golang` |
| Метрики PostgreSQL | готовый экспортер `postgres-exporter` (sidecar-контейнер в поде Postgres) |
| Модель сбора | pull, обнаружение таргетов через service discovery по аннотациям `prometheus.io/*` |

Схема:

```
под api (ns sre)        :9090/metrics   ─┐
под postgres (ns sre)                    ├─ service discovery по аннотациям ─► Victoria Metrics (ns monitoring, :8428)
  контейнер postgres-exporter :9187      ┘
```

## 2. Victoria Metrics

Victoria Metrics установлена helm-чартом по инструкции.

В `vm-single-values.yaml` я включил `server.scrape.enabled: true`. В этом режиме Victoria Metrics сама опрашивает таргеты, а встроенный конфиг чарта содержит job `kubernetes-pods`: он обнаруживает поды через Kubernetes API и оставляет только те, у которых есть аннотация `prometheus.io/scrape: "true"`; порт и путь берёт из `prometheus.io/port` и `prometheus.io/path`. Отдельный vmagent при этом не нужен, его функции выполняет встроенный в Victoria Metrics механизм скрейпа. Состояние таргетов видно на `http://localhost:8428/targets`.

## 3. Метрики рантайма

Для экспорта метрик рантайма я использовал готовые коллекторы библиотеки `client_golang` (пакет `internal/metrics`):

- `NewGoCollector` — `go_goroutines`, `go_memstats_*`, `go_gc_*` и другие метрики рантайма Go;
- `NewProcessCollector` — `process_cpu_seconds_total`, `process_resident_memory_bytes`, `process_open_fds`;
- `NewBuildInfoCollector` — `go_build_info`.

Дополнительно я добавил технические метрики HTTP-сервера через middleware, который уже писал логи запросов:

- `sre_http_requests_total{method,route,code}` — число запросов;
- `sre_http_request_duration_seconds{method,route}` — гистограмма длительности;
- `sre_http_requests_in_flight` — запросы в обработке.

В label `route` попадает шаблон маршрута (`/api/services/{id}`), а не сырой путь, иначе каждый id создавал бы новую серию и кардинальность росла бы без ограничения.

Метрики отдаются по `GET /metrics` на отдельном порту `9090` без авторизации. Этот порт не опубликован в Service `api` (он отдаёт наружу только 8080), поэтому метрики доступны лишь внутри кластера, как и требуется в задании. Формат — Prometheus text; при запросе с `Accept: application/openmetrics-text` отдаётся OpenMetrics.

## 4. Метрики PostgreSQL

В StatefulSet `postgres` я добавил второй контейнер — `postgres-exporter` (порт `9187`). Контейнеры одного пода делят сетевое пространство, поэтому экспортер подключается к базе по `localhost:5432`. Строка подключения хранится в Secret `db-credentials` (ключ `PG_EXPORTER_DSN`) и передаётся в переменную `DATA_SOURCE_NAME`. На под добавлены аннотации:

```yaml
annotations:
  prometheus.io/scrape: "true"
  prometheus.io/port: "9187"
  prometheus.io/path: "/metrics"
```

Из метрик экспортера полезны: `pg_up` (доступность базы), `pg_stat_database_numbackends` (число соединений), `pg_stat_database_xact_commit` / `xact_rollback` (транзакции), `pg_stat_database_blks_hit` / `blks_read` (попадания в кэш), `pg_locks_count`.

## 5. Service discovery

В Deployment `api` и StatefulSet `postgres` в шаблон пода добавлены аннотации `prometheus.io/scrape`, `prometheus.io/port`, `prometheus.io/path`, а порты объявлены в `containerPort` (`metrics: 9090` у API, `metrics: 9187` у экспортера) — встроенный job сопоставляет порт из аннотации с объявленным портом контейнера. Таргеты не прописываются в конфигурации Victoria Metrics: новый под с такими аннотациями подхватывается автоматически, в том числе при масштабировании `api` до нескольких реплик.

## 6. Бизнес-метрики

Я реализовал 9 метрик предметной области (каталог сервисов и учёт инцидентов):

| Метрика | Тип | Labels | Смысл |
|---|---|---|---|
| `sre_incidents_created_total` | counter | `severity` | сколько инцидентов заведено |
| `sre_incidents_resolved_total` | counter | `severity` | сколько инцидентов закрыто (переход в `resolved`) |
| `sre_incident_status_transitions_total` | counter | `from`, `to` | переходы между статусами, показывает, как инциденты проходят процесс обработки |
| `sre_incident_resolution_duration_seconds` | histogram | `severity` | время от создания до решения, основа для расчёта MTTR |
| `sre_incidents_deleted_total` | counter | — | удалённые инциденты |
| `sre_services_created_total` | counter | — | добавленные сервисы |
| `sre_services_deleted_total` | counter | — | удалённые сервисы |
| `sre_incidents_current` | gauge | `status`, `severity` | сколько инцидентов сейчас |
| `sre_services_current` | gauge | — | сколько сервисов сейчас |

Как это устроено:

- счётчики увеличиваются в HTTP-обработчиках только после успешной операции в БД, ошибочные запросы в них не попадают;
- при обновлении инцидента обработчик сначала читает его предыдущее состояние и считает переход, только если статус действительно изменился;
- gauge `*_current` вычисляются специальным коллектором: в момент скрейпа он делает запросы `GROUP BY status, severity` к БД. Так значение всегда соответствует реальному состоянию и не зависит от числа реплик и перезапусков (счётчик в памяти после рестарта обнулился бы, а состояние нужно хранить в БД);
- серии с известными значениями `severity` и `status` создаются заранее со значением 0, чтобы метрики были видны с первого скрейпа и корректно работали `rate()` и `increase()`.
